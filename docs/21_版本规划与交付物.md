## 5. V2.0（规划定稿 2026-09-28）

决策：全做 A+B+C 三阶段；IPC 用 QLocalSocket（JSON 行协议）；Linux 搁置（待环境，#else 空实现已保证可移植性）。

### Phase A：数据增值（纯增量，低风险）
- CSV / JSON 批量数据输出：慢事件记录、MetaCall 记录落盘（超越报告导出的"最近诊断快照"，支持全量回放分析）。
- 统计导出增强：EventStatistics 周期快照 TOP-N / 耗时分位数并入导出。
- 自动生成性能诊断摘要：基于已捕获数据的规则化归因（主线程阻塞 TOP、高频信号、QSS 抖动嫌疑），txt/json 双格式。

### Phase B：IPC 配置（旗舰项）✅ 已完成（2026-09-28）
- QLocalSocket 服务端 + JSON 行协议：运行时动态改 Watch_Fun / 各阈值 / 匿名开关 / blacklist。
- 复用 WatchConfig setter 与 QWriteLocker 原子替换通道（与 INI 热更新同构）。
- 配套 Demo 控制台（发送端），验证"外部进程实时调控被测程序监控行为"。
- 安全约束：协议解析失败静默丢弃 + WARN；无认证（本机命名管道，PRD 14 威胁模型内）。
- 实施记录：IpcConfigServer（src/ipc/，非 QObject 组合式，信号槽驱动主线程处理）；
  协议 op=get / set / filter.add / filter.clear（filter.clear 复位全部规则含匿名开关）；
  监听名 QtEventWatcher.<pid>（多实例隔离，QT_EVENT_WATCHER_IPC_NAME 可覆盖）；
  单行 8KB 上限防恶意客户端。端到端实测：控制台 set watchFun=0 → 4s 窗口告警 28→1 条
  （静默），恢复 15 → 31 条；畸形请求（PowerShell 引号剥离实战注入）被正确静默丢弃 + WARN。

### Phase C：补全 ✅ C1/C2 已完成（2026-09-28），C3 搁置
- Thread Registry ✅：sender QThread* 安全注册表（发射时刻注册，析构时刻注销），补 senderThread 精确语义。
- Exclusive Cost 聚合统计 ✅：周期快照新增 Exclusive 维度聚合（线程内自耗时归因）。
- Linux 验证：搁置，待环境（静态风险已由 #else 分支控制）。
- 实施记录：ThreadRegistry（src/event/，指针值键 + destroyed 自动注销 + isCurrentThread
  回填 os id + 64 条上限降级；isCurrentThread 用 `== QThread::currentThread()` 跨版本写法，
  Qt6.9+ 同名 API 不依赖）；SenderRegistry 发射时刻 `sender->thread()` 安全解引用（仅此一处），
  SenderIdentity 新增 ownerThreadId，MetaCallWatcher 输出归属线程优先、未观测回退发射线程；
  EventStatistics record() 新增 exclusiveNs 入参（EventStat/StatEntry 加 exclusiveTotal/MaxNs，
  热路径仅两次整数比较累加），JSON 统计段与诊断摘要 StatTop 并入 exclusive 维度。
- GUI 级验证（MinGW5，SlowMetaCall=1ms 压力 9s）：109 条带 sender 告警，timeout()=103
  无误判；同线程源 senderThread==recvThread（match=true 81 条），跨线程源
  senderThread=0x9e7c ≠ recvThread（match=false 28 条）——归属语义精确可观测。

### Phase D：性能基准报告 ✅ 已完成（2026-09-28）
- BenchmarkEventWatcher harness（tests/benchmark/，不进 CTest）：同进程对照法
  （`QCoreApplication::notify` 限定基类调用 vs 虚调用覆写）量化监控纯增量；
  模式 off / event / slow / metacall_on / metacall_off，配置经 qputenv 启动前注入。
- 四矩阵实测（ns/op，avg）：①覆写固定开销 131~140（全关常驻）②正常路径 657~854
  （含快照与统计入表）④spy 回调增量 +31~62/emit；③告警路径 27~37µs（仅慢事件付费，
  含 spdlog 全 sink 落盘）。对照 16.6ms 帧预算：常驻 0.00084%，高频极端负载 CPU <1.5%。
- 报告：docs/22_性能基准报告.md（环境/方法论/结果/帧预算分析/复现方法/局限性）。

依赖关系：诊断摘要依赖统计导出的数据结构（A 内部串行）；IPC 与 A 无依赖可并行；C 依赖 B 的注册表经验；D 依赖 A~C 全部落地后测终态开销。

## 6. V3.0（规划定稿 2026-09-28）

决策：A 线归因深化先行（调用栈 + 风暴抑制）；B 线冻结观测（看门狗+取证）、C 线数据消费（HTML 报告/SQLite/多进程）、D 线工程守护（CI 基准/Linux/API 收紧）列入候选池，A 线落地后再定追加项。

### Phase A1：慢事件调用栈采集（归因从"事件级"到"函数级"）
- 采集时机：仅告警路径——慢事件 / 慢 MetaCall 命中阈值后采集，热路径零成本（PRD 14 模型延续）。
- 采集内容：`RtlCaptureStackBackTrace` ≤32 帧 → {模块基址, 模块名, 模块内偏移} 快照；
  非 Windows `#else` 返回空帧（可移植性约定同 C3）。
- 符号化策略：**采集侧零 dbghelp 依赖**（SymInitialize 首次加载可达百 ms 级，禁止进告警路径，
  否则监控器在用户最卡的时刻放大卡顿）；默认输出 `模块名!偏移`，符号解析放导出侧
  （DataExporter 可选符号化，默认关）或离线工具，需 PDB/MinGW debug info。
- 数据出口：告警日志行附加 `stack=模块!off,模块!off,...`；WatchRecordStore 结构化记录
  新增 frames 字段（随导出进 CSV/JSON）；帧数据不进 WatchEventInfo（公共头不膨胀）。
- 范围：EventWatcher 与 MetaCallWatcher 告警路径统一能力（MetaCall 栈即槽执行栈，同价值）。

### Phase A2：告警风暴抑制
- 问题定性：高频定时器/逐帧卡顿时同类 WARN 可达 100 条/s，日志 IO 在卡顿窗口内放大负载
  （监控器自身成为负担，违背 PRD 14 精神；V1.3 验证中 4s 28 条 timeout() 已见端倪）。
- 语义：同类告警（Event: receiver+事件类型；MetaCall: sender+signal）在窗口（1s）内首条必出，
  后续静默累计，窗口关闭时输出一条 `suppressed=N` 汇总——不丢总量，只去重风暴。
- 边界：仅作用于告警日志；EventStatistics::record 与 WatchRecordStore 保留全量逐条
  （回放数据完整性优先）；判定位置在阈值判断之后、日志输出之前（既有性能约定）。
- 配置：窗口先用编译期常量 1000ms（不加配置项），实测后再评估是否入 WatchConfig。

依赖关系：A2 独立于 A1 可并行；每阶段四矩阵编译 + 冒烟 + 告警路径 GUI 实测
（沿用 MinGW5 demo + QT_EVENT_WATCHER_SLOW_METACALL_THRESHOLD_MS=1 压力手段）。

## 8. 项目成功标准
工具能够在不依赖 Qt Profiler / Visual Studio Profiler 的情况下，为 Qt Widgets 程序提供足够精确、低开销、可落盘的卡顿线索，并且监控器自身不成为新的性能问题来源。
