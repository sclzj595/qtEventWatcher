### Phase A2：告警风暴抑制 ✅ 已完成（2026-09-28）
- 问题定性：高频定时器/逐帧卡顿时同类 WARN 可达 100 条/s，日志 IO 在卡顿窗口内放大负载
  （监控器自身成为负担，违背 PRD 14 精神；V1.3 验证中 4s 28 条 timeout() 已见端倪）。
- 语义：同类告警（Event: receiver+事件类型；MetaCall: sender+signal）在窗口（1s）内首条必出，
  后续静默累计，窗口关闭时输出一条 `suppressed=N` 汇总——不丢总量，只去重风暴。
- 边界：仅作用于告警日志；EventStatistics::record 与 WatchRecordStore 保留全量逐条
  （回放数据完整性优先）；判定位置在阈值判断之后、日志输出之前（既有性能约定）。
- 配置：窗口先用编译期常量 1000ms（不加配置项），实测后再评估是否入 WatchConfig。
- 实施记录：AlarmSuppressor（src/event/，互斥 + unordered_map<key,WindowState>，
  startMs=-1 哨兵避免 t=0 误判；懒冲刷——风暴停止后汇总在该 key 下次告警时补出，零定时器；
  evaluate(key, nowMs) 合成时钟注入供测试确定性）。级别路由：logger 门放宽至
  min(用户级别, debug)，文件/控制台 sink 显式按用户级别过滤，RecordSink 降至 debug
  （静默条以 DEBUG 发出被全量采集），WatchLogCapture 保持 warn（UI 只见 WARN+）。
  CMake PUBLIC 定义 SPDLOG_ACTIVE_LEVEL=SPDLOG_LEVEL_DEBUG（spdlog 默认 INFO 会把
  DEBUG 宏编译期剥离为空——实测踩坑）。四矩阵编译 + 冒烟（合成时钟决策断言 +
  存储全量 4/4 + INFO 排除）全绿；MinGW5 GUI 压测（watchFun=15 + SlowMetaCall=1ms，12s）：
  MetaCall 文件告警 333→33 条 WARN（10× 去重）+ 36 条 storm 汇总（suppressed=14/16/5…），
  文件 0 条 DEBUG 泄漏，WatchRecordStore 全量逐条保留。

依赖关系：A2 独立于 A1 可并行；每阶段四矩阵编译 + 冒烟 + 告警路径 GUI 实测
（沿用 MinGW5 demo + QT_EVENT_WATCHER_SLOW_METACALL_THRESHOLD_MS=1 压力手段）。

### Phase B1：冻结观测与看门狗 ✅ 已完成（2026-09-28）

- 问题定性：长任务/死锁/模态阻塞导致主线程事件循环停摆；既有事件级监控依赖事件
  派发，冻结窗口内自身同样停摆，无法自证卡死。
- 语义（ANR 模式）：主线程挂心跳 QTimer（冻结即停跳），EventWatchdog 常驻
  std::thread 以 100ms 粒度轮询心跳时间戳，停滞超阈值即判定冻结。"空闲"不误报
  （空闲时定时器到期仍唤醒派发）；恢复判定以"心跳前进"为准（beat 时间戳快照对比，
  不依赖节拍精度），freezeStartMs 取最后一次心跳时刻 → totalMs 精确。
- 三态告警：started（WARN，附取证快照）→ ongoing（1s 节流，自带节流不经
  AlarmSuppressor）→ recovered（含总时长）；均由看门狗线程发出（spdlog _mt）。
- 取证快照：notify 入口 eventStarted 记录"正在处理的事件"（receiver 类名 + 事件
  类型），出口 eventFinished 清除，冻结时即"卡在哪个事件"。两个实测踩坑：
  1) 基类 QApplication 构造/析构阶段（qwindows 平台插件初始化）即派发事件进入
     notify，此时成员 m_watchdog 尚未创建/已销毁——必须判空，否则 0xC0000005
     （GUI 崩溃定位 3 轮：main-enter 探针 → trace_ctor 探针 → 崩溃点锁定基类构造期）；
  2) notify 是全进程虚函数，worker 线程（demo 中 moveToThread 的 crossThreadTimer，
     300ms 周期）派发事件同样进入，单例快照被 worker 事件反复覆盖，取证失真
     （esTrace 文件探针 + BEAT 交错分析定位）——修复为构造线程绑定（=心跳线程）
     写入，非心跳线程一次 thread::id 比较零开销早退。
- 配置：WatchFreeze bit4（WatchAll=31）；FreezeThresholdMs 默认 2000ms /
  HeartbeatIntervalMs 默认 250ms；环境变量 QT_EVENT_WATCHER_FREEZE_THRESHOLD_MS /
  QT_EVENT_WATCHER_HEARTBEAT_INTERVAL_MS（纯十进制）+ INI（FreezeThresholdMs /
  HeartbeatIntervalMs）+ IPC setter 三通道热更新；开关 run() 每轮实时查询。
- 链路：KindFreeze 入 WatchRecordStore（4096 环形，raw 前缀 "[FreezeWatch] "）、
  CatFreeze 入 WatchLogCapture（GUI 明细分类）、DataExporter kind=freeze +
  JSON counts.freezeEvents。
- 接入：CusApplication 构造尾部创建 watchdog + 心跳 QTimer（心跳周期热更新跟随
  重启，同 configTimer 模式）；notify 挂 eventStarted/eventFinished（判空）。
  Demo：测试页"制造 UI 冻结 3s"按钮 + basic_demo --autofreeze <ms> 自动化入口
  （启动 1.5s 后主线程 msleep）；监控状态点纳入 bit4。
- 验证：四矩阵编译 + 冒烟全绿（threshold=200ms/heartbeat=50ms 合成冻结
  started=1/recovered=1 数量对齐 + 关门静默 + 快照 (unknown)/type=0 断言）；
  Qt5 MSVC GUI 实测（WATCH_FUN=16 + --autofreeze 3000）：started stalledMs=2063
  receiver=QSingleShotTimer type=1 inProgress=true → ongoing → recovered
  totalMs=3269——取证精准命中 msleep 载体事件，优雅关闭 exit=0。

  进 notify，160~182ns 仍为帧预算 0.001%）；② 正常路径同量级（610~952ns）；

  主增量为 A1 栈采集格式化 + 懒冲刷双行落盘，仅由已达阈值事件付费）。
- 归因代码依据：EventWatcher.cpp 告警路径中栈采集在抑制判定**之前**（设计取向：
  全量记录含 frames 优先于抑制省费）——"栈采集移到抑制之后"已列为候选优化

- 教训：改 benchmark 嵌套 if 结构时 else-if 链被内层 if 抢走（大括号平衡但

  非法/namespace not allowed"——报错在 moc 生成物，根因在宿主 .cpp 作用域。

### Phase A1：WatchRecordStore 懒解析 ✅ 已完成（2026-09-29）

- **sink 端零解析**：环形缓冲只存 kind/seq/time/raw（parseFields ~20 次 substr 分配 + parseFrames 从 sink_it_ 移除）——风暴期无消费则零解析成本；顺带降低 4096 条环形内存占用与快照持锁拷贝时长；
- **快照出口 hydrate**：snapshot()/snapshotSince() 锁外逐条重建 fields/frames（顺序与 V4 采集端逐条等价：QSS op 提取 → parseFields → stack= 拆帧）——公共 API 语义不变，"全量记录"语义保全；
- **解析单点化**：hydrateRecord/parseFields/parseFrames 提升为 WatchRecordStore 公有静态方法（extractQssOp 经 hydrateRecord 内化）——A2 aggregator 复用免拷贝实现；
- **formatTime 秒段缓存**：localtime_s 是函数大头，同秒只渲染一次（sink_it_ 由 base_sink\<std::mutex\> 串行，普通 static 无竞态）；
- 验证：四矩阵编译 + 冒烟全绿（DiagnosticSummarizer/DataExporter 的 fields 消费断言即逐字段等价的行为级验证）。

### Phase A2：上行协议 raw 化 ✅ 已完成（2026-09-29）

- aggregator 增 rebuildStructured()：用 WatchRecordStore::hydrateRecord 消费侧重建 fields/frames，存储与 JSON 导出形状与 V4 一致（fields=[[k,v]..]/frames=[[mod,off]..]）；
