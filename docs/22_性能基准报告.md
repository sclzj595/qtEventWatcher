# Qt 卡顿排查辅助器 PRD 22：性能基准报告

## 1. 目的与验收依据

量化监控器自身开销，验证 PRD 14 §5 关键原则——"监控器自身不能成为卡顿来源，更不能因为监控导致被测程序行为发生明显改变"——以及 PRD 20 §4 验收原则（监控功能失败不影响核心业务）。

监控器所有开销分为四条线，逐条给出常驻成本与触发条件：

| 开销线 | 触发条件 | 代码路径 |
|---|---|---|
| ① notify 覆写固定开销 | 进程使用 CusApplication 即常驻（即使 Watch_Fun=0） | notify 入口：thread_local 嵌套管理 ×2 + EventGuard 计时 + isEnabled() 短路 |
| ② 开启后正常路径 | Watch_Event/Watch_EventStatistics 开启，事件低于阈值 | watchEvent 快照（metaObject/objectName/线程）+ EventStatistics::record |
| ③ 告警路径 | 仅超过阈值的慢事件 | 完整字段格式化 + spdlog 4 sink（控制台 + rotating 文件 flush_on(warn) + 捕获环形 32 + 结构化记录环形 4096） |
| ④ 信号发射 spy 回调 | 仅 Watch_MetaCall 开启时安装注册表 | MetaCallSenderRegistry::onSignalBegin（互斥锁 + 环形快照 + 签名表查缓存） |

## 3. 方法论

- Harness：`tests/benchmark/BenchmarkEventWatcher.cpp`（新增，不进 CTest），模式经启动前 `qputenv` 注入配置，分进程运行：`off` / `event` / `slow` / `metacall_on` / `metacall_off`。
- **同进程对照法**：基线以限定名调用 `app.QCoreApplication::notify(receiver, &event)` 绕过监控覆写（等价于未安装监控器的 Qt 原生分发）；被测为虚调用 `app.notify(...)`。两者之差即监控纯增量，排除机器与事件本身的噪声。
- 每场景先预热 1 轮，再测 7 轮（告警路径 3 轮），报告 ns/op 的 avg 与 min；取 avg 计算增量。
- 慢事件用忙等接收者（自旋 1.2ms）模拟真实超阈值处理；告警路径数字**包含真实日志落盘**（spdlog 全 sink 挂载，与 Demo 部署形态一致）。
- 信号发射用直连信号（不经事件队列）隔离 spy 回调增量；`metacall_off` 进程（未安装注册表）作发射基线。
- IPC 服务端随 CusApplication 启动（与生产形态一致）：QLocalServer 为事件驱动，无请求时零轮询成本；INI 热更新轮询 60s 一次 mtime stat，可忽略。

## 4. 结果（四矩阵，单位 ns/op，avg）

| 场景 | 5.15.2 MSVC | 6.5.3 MSVC | 5.15.2 MinGW | 6.5.3 MinGW |
|---|---:|---:|---:|---:|
| 基线 notify（普通事件） | 7.2 | 11.2 | 4.1 | 5.6 |
| ① 覆写固定开销（off 增量，Watch_Fun=0） | **131.5** | **140.1** | **137.5** | **138.5** |
| ② 开启后正常路径增量（低于阈值） | **657.1** | **820.4** | **853.6** | **690.9** |
| record() 微基准（单次统计入表，含锁） | 301.7 | 625.7 | 284.9 | 307.7 |
| ④ emit 基线（无 spy 回调） | 26.9 | 30.3 | 29.2 | 28.7 |
| ④ emit（spy 回调已安装） | 66.7 | 92.4 | 63.6 | 60.0 |
| ④ spy 回调增量 | **+39.8** | **+62.1** | **+34.4** | **+31.3** |
| ③ 告警路径增量（1.2ms 慢事件，含日志落盘） | **36 800.7** | **31 438.1** | **27 127.3** | **29 942.6** |

观察：
- ① 四矩阵高度一致（131~140ns）：路径全部为无分配的整数/原子操作，与编译器、Qt 版本无关。
- ② MinGW 5.15.2 略高（853ns）：objectName/metaObject 快照的 QString 分配成本差异；量级不变。
- record() 在 6.5.3 MSVC 偏高（626 vs ~300ns）：QReadWriteLock 在 Qt 6 实现差异，量级仍在亚微秒。
- ③ 告警路径 27~37µs，成本主要在同步文件写入 + flush_on(warn)，是"告警才付费"的典型形态。

## 5. 分析：对照 16.6ms 帧预算（60 FPS）

| 开销线 | 最坏实测 | 单次占帧预算 | 高频极端负载下 CPU 占比估算 |
|---|---:|---:|---|
| ① 覆写固定 | 140 ns | 0.00084% | 10 万事件/秒 → 14 ms/s ≈ **1.4%** |
| ② 正常路径 | 854 ns | 0.0051% | 1 万事件/秒 → 8.5 ms/s ≈ **0.85%** |
| ④ spy 回调 | 62 ns/emit | — | 10 万次发射/秒 → 6.2 ms/s ≈ **0.62%** |
| ③ 告警路径 | 37 µs | 0.22% | 仅慢事件付费；对 1.2ms 慢事件自身附加 3.1%，且此时事件本身已构成卡顿 |

关键结论：
1. **常驻成本可忽略**：全关时每事件 140ns（帧预算的 0.00084%），开关判断先行（isEnabled 短路）满足 PRD 14 §1"关闭功能时快速 return"。
2. **正常路径付费可控**：开启监控后每事件亚微秒（0.65~0.85µs），含线程快照与统计入表；即使极端高频事件流，CPU 占比 <1%。
3. **告警路径隔离**：重成本（格式化 + 文件 IO）仅发生在已超阈值的事件上——此时业务已经卡顿，30µs 的诊断开销不会改变"已卡顿"的事实，符合 PRD 14"仅在启用监控且达到阈值时执行完整异常处理"。
4. **热路径零动态分配兑现**：正常路径不产生日志（PRD 14 §1），发射回调仅查表与固定缓冲覆写（PRD 06）；这正是 ②④ 保持在亚微秒/百纳秒量级的原因。

## 6. 复现方法

```powershell
# 构建（以 5.15.2 MSVC 为例；其余矩阵同理）
cmake --build build --target BenchmarkEventWatcher --config Release

# 运行（需 Qt bin 在 PATH；在独立目录运行以隔离 logs）
cd build\bench-runs\qt5152-msvc
..\..\bin\Release\BenchmarkEventWatcher.exe off
..\..\bin\Release\BenchmarkEventWatcher.exe event     # 含 record() 微基准
..\..\bin\Release\BenchmarkEventWatcher.exe slow      # 告警路径（控制台会被告警刷屏，过滤 ^scenario= 行）
..\..\bin\Release\BenchmarkEventWatcher.exe metacall_on
..\..\bin\Release\BenchmarkEventWatcher.exe metacall_off
```

## 7. 局限性

- 数值为本机单机实测，绝对值受 CPU 频率/负载影响，量级与相对关系（①≪②≪③）跨矩阵稳定。
- 告警路径含控制台 sink 的同步写；若宿主程序重定向控制台，该项可能有波动。
- 未覆盖 Linux（C3 搁置，与整体计划一致）；IPC 仅定性（事件驱动零轮询），未做压测——协议处理在主线程事件循环，请求频率由调用方控制，不属于常驻开销。

## 8. V3 终态基准回归（2026-09-28）

V3 的 A 线（调用栈采集 + 风暴抑制）、B 线（冻结看门狗）、C 线（SQLite/HTML 导出，不进热路径）全部落地后，按规划"D 依赖 A~C 全部落地后测终态开销"复测四矩阵。Harness 扩展：`slow` 模式 tight-loop 场景在 A2 抑制器生效后测得的是**风暴抑制路径**（首条落盘 + 后续静默）；新增 `busy-user-event-alert-first` 场景（每条间隔 1.1s > 1s 抑制窗口，逐条完整告警落盘，与绕过监控基线同间隔对照）。

| 场景 | 5.15.2 MSVC | 6.5.3 MSVC | 5.15.2 MinGW | 6.5.3 MinGW |
|---|---:|---:|---:|---:|
| ① 覆写固定开销（off 增量） | **180.0** | **159.9** | **181.5** | **165.9** |
| ② 开启后正常路径增量 | **952.0** | **896.4** | **653.7** | **726.4** |
| record() 微基准 | 315.1 | 396.4 | 266.1 | 298.1 |
| ④ emit 基线（无 spy 回调） | 25.0 | 30.0 | 26.6 | 26.8 |
| ④ spy 回调增量 | **+39.1** | **+58.0** | **+34.3** | **+34.3** |
| ③ 风暴抑制路径（tight-loop，V2 同场景为全告警 27~37µs） | **18 588.3** | **18 363.3** | **15 605.6** | **18 286.8** |
| ③ 完整告警路径（alert-first，V2 同语义 27~37µs） | **110 260.0** | **125 400.0** | **127 920.0** | **152 580.0** |

观察与归因：

- **① 常驻 +25~45ns**（131~140 → 160~182）：B1 看门狗 eventStarted/eventFinished 挂入 notify（判空 + 心跳线程 thread::id 比较 + 取证快照写入）。量级不变，仍为帧预算的 0.001%。
- **② 正常路径同量级**（610~952ns）：快照路径新增看门狗写入与线程注册表，最坏 952ns 仍占帧预算 0.006%。
- **④ 发射路径持平**（+34~58ns/emit）：V3 未触碰 MetaCall 发射回调。
- **③ 风暴抑制路径比 V2 全告警低约一半**（27~37µs → 15.6~18.6µs）：A2 达成设计目标——风暴期间每条只付"栈采集 + 全量记录 + DEBUG sink"，文件 IO 仅首条付费。占 1.2ms 慢事件自身 1.3~1.6%（V2 为 2.3~3.1%）。
- **③ 完整告警路径约 3.4×**（V2 27~37µs → 110~153µs）：构成为 A1 调用栈采集与格式化（≤32 帧 capture + GetModuleHandleEx 归属 + `模块!偏移` 串拼接，占主要增量）+ 首条滞后冲刷的 storm 汇总行（懒冲刷双行落盘）+ V2 既有的格式化与 4 sink 落盘。**仅由已达阈值的慢事件付费**：对 1.2ms 慢事件附加 9.2~12.7%（V2 为 2.3~3.1%）——该事件本身已构成卡顿，诊断信息（调用栈）换此开销符合 PRD 14 精神，但已列入候选优化：若未来要求更低，可将栈采集移到抑制判定之后（代价 = 被抑制事件的记录失去 frames 字段，违背"全量记录"语义）或下调抑制场景的帧数上限。
- record() 持平（266~396ns），C 线导出为显式动作不进热路径，无数字变化。

关键结论（V3 终态）：四条开销线量级关系维持 ①≪②≪④≪③；常驻与正常路径的回归可忽略（+45ns 内），风暴路径减半，仅"首条告警"以 3.4× 换取函数级归因能力——监控器仍不成为新的卡顿来源。

## 9. V4 B2 栈采集三档复测（2026-09-29）

StackCaptureMode 三档落地后，在 `busy-user-event-slow`（tight-loop，测得风暴抑制路径）复测 Qt5 MSVC 单矩阵：

| 档位 | 语义 | avg |
|---|---|---:|
| mode=0（默认） | 命中即采（记录全量含 frames） | 16.8µs |
| mode=1 | 仅窗口首条采（被抑制条免采，记录无 frames） | 10.7µs |
| mode=2 | 全免采 | （与 mode=1 同级，未单列） |

mode=1 相对 mode=0 省 **-36%（约 6µs）**，低于规划预期 ≤5µs 增量的估算口径。归因洞察：抑制路径的大头是**告警日志格式化 + RecordSink 结构化采集**（~10µs），栈采集本身仅 ~6µs——B2 只能压缩后者的时机，前者按 A2 语义（全量记录）必须保留。mode=1 的取舍明确：**记录失去 frames 字段**（仅窗口首条带栈），换取风暴期更低的记录路径开销；默认档保持 0（全量归因），mode=1/2 留给高吞吐场景显式开启。

与 §8 ③ 完整告警路径（110~153µs）的关系：alert-first 场景逐条走完整告警（含文件 IO），B2 三档只影响"栈采集"一段（~6µs），对完整告警路径增量有限；风暴抑制路径（15.6~18.6µs）才是三档的主战场。

## 10. V5 A 线采集链路瘦身复测（2026-09-29）

V5 A1（sink 端零解析，字段解析后移到 snapshot 出口锁外 hydrate）+ A2（上行协议 raw 化）落地后，`slow` 模式（busy-user-event-alert 的 delta_avg = 风暴抑制路径）复测 Qt5 MSVC，每档多轮取稳定值：

| 档位 | V4 B2 基线（§9） | V5 A3 复测 | 结论 |
|---|---:|---:|---|
| mode=0（默认） | 16.8µs | 15.1~16.6µs（3 轮中位） | 持平（首跑 20.7µs 为冷启动噪声） |
| mode=1 | 10.7µs | **9.3~9.5µs** | **-1.2~1.4µs（约 -12%）** |
| mode=2 | （与 mode=1 同级） | 10.3µs | 与 mode=1 同级 |
| ② 正常路径（plain delta） | 610~952ns | 687~790ns | 持平（V4 区间内） |

**诚实归因：收益低于规划预期（预期 6~8µs）**。A 线移除的是 sink 端 parseFields/parseFrames（~20 次 substr 小分配），实测仅 ~1.3µs——现代 allocator 下小额分配远比估算便宜（规划按 2~4µs 估算偏高）。剩余 ~9.4µs 地板构成：fmt 实参替换（12 实参）+ payload 字符串拷贝 + formatTime + 4 sink 分发 + 环形入队。

**V5 A 线的真实收益主要是架构性的**：①监控端全链路零字段解析（风暴期无消费则零解析成本，消费时也缩短快照持锁时长）；②4096 条环形内存占用降低（不再存 fields/frames 容器）；③解析逻辑单点化（hydrateRecord 公有静态，aggregator 复用免拷贝实现）。性能上 mode=1 的 -1.3µs 是搭车收益。

**基线与容差处理**：`-UpdateBaselines` 刷新 23 keys × 4 矩阵；`busy-user-event-alert` 按 alert-first 先例移入 excludeScenarios——噪声态下单次摆动实测 12~25µs（±40%）跨容差带（qt6 复跑 17.2/19.1/22.7µs 跨基线两侧即证），③ 告警路径数字改由本报告逐版本多轮复测守门。DRIFT 本为提示级（-Strict 才阻断），排除后回归 4/4 PASS 无告警噪声。
