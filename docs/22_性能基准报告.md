# Qt 卡顿排查辅助器 PRD 22：性能基准报告

## 1. 目的与验收依据

量化监控器自身开销，验证 PRD 14 §5 关键原则——"监控器自身不能成为卡顿来源，更不能因为监控导致被测程序行为发生明显改变"——以及 PRD 20 §4 验收原则（监控功能失败不影响核心业务）。

监控器所有开销分为四条线，逐条给出常驻成本与触发条件：

| 开销线 | 触发条件 | 代码路径 |
|---|---|---|
| ① notify 覆写固定开销 | 进程使用 CusApplication 即常驻（即使 Watch_Fun=0） | notify 入口：thread_local 嵌套管理 ×2 + EventGuard 计时 + isEnabled() 短路 |
| ② 开启后正常路径 | Watch_Event/Watch_EventStatistics 开启，事件低于阈值 | watchEvent 快照（metaObject/objectName/线程）+ EventStatistics::record |
| ③ 告警路径 | 仅超过阈值的慢事件 | 完整字段格式化 + spdlog 4 sink（控制台 + rotating 文件 flush_on(warn) + 捕获环形 32 + 结构化记录环形 4096） |
| ④ 信号发射 spy 回调 | 仅 Watch_MetaCall 开启时安装注册表 | MetaCallSenderRegistry::onSignalBegin（互斥锁 + 环形快照 + 签名表查缓存） |

## 3. 方法论

- Harness：`tests/benchmark/BenchmarkEventWatcher.cpp`（新增，不进 CTest），模式经启动前 `qputenv` 注入配置，分进程运行：`off` / `event` / `slow` / `metacall_on` / `metacall_off`。
- **同进程对照法**：基线以限定名调用 `app.QCoreApplication::notify(receiver, &event)` 绕过监控覆写（等价于未安装监控器的 Qt 原生分发）；被测为虚调用 `app.notify(...)`。两者之差即监控纯增量，排除机器与事件本身的噪声。
- 每场景先预热 1 轮，再测 7 轮（告警路径 3 轮），报告 ns/op 的 avg 与 min；取 avg 计算增量。
- 慢事件用忙等接收者（自旋 1.2ms）模拟真实超阈值处理；告警路径数字**包含真实日志落盘**（spdlog 全 sink 挂载，与 Demo 部署形态一致）。
- 信号发射用直连信号（不经事件队列）隔离 spy 回调增量；`metacall_off` 进程（未安装注册表）作发射基线。
- IPC 服务端随 CusApplication 启动（与生产形态一致）：QLocalServer 为事件驱动，无请求时零轮询成本；INI 热更新轮询 60s 一次 mtime stat，可忽略。

## 4. 结果（四矩阵，单位 ns/op，avg）

| 场景 | 5.15.2 MSVC | 6.5.3 MSVC | 5.15.2 MinGW | 6.5.3 MinGW |
|---|---:|---:|---:|---:|
| 基线 notify（普通事件） | 7.2 | 11.2 | 4.1 | 5.6 |
| ① 覆写固定开销（off 增量，Watch_Fun=0） | **131.5** | **140.1** | **137.5** | **138.5** |
| ② 开启后正常路径增量（低于阈值） | **657.1** | **820.4** | **853.6** | **690.9** |
| record() 微基准（单次统计入表，含锁） | 301.7 | 625.7 | 284.9 | 307.7 |
| ④ emit 基线（无 spy 回调） | 26.9 | 30.3 | 29.2 | 28.7 |
| ④ emit（spy 回调已安装） | 66.7 | 92.4 | 63.6 | 60.0 |
| ④ spy 回调增量 | **+39.8** | **+62.1** | **+34.4** | **+31.3** |
| ③ 告警路径增量（1.2ms 慢事件，含日志落盘） | **36 800.7** | **31 438.1** | **27 127.3** | **29 942.6** |

观察：
- ① 四矩阵高度一致（131~140ns）：路径全部为无分配的整数/原子操作，与编译器、Qt 版本无关。
- ② MinGW 5.15.2 略高（853ns）：objectName/metaObject 快照的 QString 分配成本差异；量级不变。
- record() 在 6.5.3 MSVC 偏高（626 vs ~300ns）：QReadWriteLock 在 Qt 6 实现差异，量级仍在亚微秒。
- ③ 告警路径 27~37µs，成本主要在同步文件写入 + flush_on(warn)，是"告警才付费"的典型形态。

## 5. 分析：对照 16.6ms 帧预算（60 FPS）

| 开销线 | 最坏实测 | 单次占帧预算 | 高频极端负载下 CPU 占比估算 |
|---|---:|---:|---|
| ① 覆写固定 | 140 ns | 0.00084% | 10 万事件/秒 → 14 ms/s ≈ **1.4%** |
| ② 正常路径 | 854 ns | 0.0051% | 1 万事件/秒 → 8.5 ms/s ≈ **0.85%** |
| ④ spy 回调 | 62 ns/emit | — | 10 万次发射/秒 → 6.2 ms/s ≈ **0.62%** |
| ③ 告警路径 | 37 µs | 0.22% | 仅慢事件付费；对 1.2ms 慢事件自身附加 3.1%，且此时事件本身已构成卡顿 |

关键结论：
1. **常驻成本可忽略**：全关时每事件 140ns（帧预算的 0.00084%），开关判断先行（isEnabled 短路）满足 PRD 14 §1"关闭功能时快速 return"。
2. **正常路径付费可控**：开启监控后每事件亚微秒（0.65~0.85µs），含线程快照与统计入表；即使极端高频事件流，CPU 占比 <1%。
3. **告警路径隔离**：重成本（格式化 + 文件 IO）仅发生在已超阈值的事件上——此时业务已经卡顿，30µs 的诊断开销不会改变"已卡顿"的事实，符合 PRD 14"仅在启用监控且达到阈值时执行完整异常处理"。
4. **热路径零动态分配兑现**：正常路径不产生日志（PRD 14 §1），发射回调仅查表与固定缓冲覆写（PRD 06）；这正是 ②④ 保持在亚微秒/百纳秒量级的原因。

## 6. 复现方法

```powershell
# 构建（以 5.15.2 MSVC 为例；其余矩阵同理）
cmake --build build --target BenchmarkEventWatcher --config Release

# 运行（需 Qt bin 在 PATH；在独立目录运行以隔离 logs）
cd build\bench-runs\qt5152-msvc
..\..\bin\Release\BenchmarkEventWatcher.exe off
..\..\bin\Release\BenchmarkEventWatcher.exe event     # 含 record() 微基准
..\..\bin\Release\BenchmarkEventWatcher.exe slow      # 告警路径（控制台会被告警刷屏，过滤 ^scenario= 行）
..\..\bin\Release\BenchmarkEventWatcher.exe metacall_on
..\..\bin\Release\BenchmarkEventWatcher.exe metacall_off
```

## 7. 局限性

- 数值为本机单机实测，绝对值受 CPU 频率/负载影响，量级与相对关系（①≪②≪③）跨矩阵稳定。
- 告警路径含控制台 sink 的同步写；若宿主程序重定向控制台，该项可能有波动。
- 未覆盖 Linux（C3 搁置，与整体计划一致）；IPC 仅定性（事件驱动零轮询），未做压测——协议处理在主线程事件循环，请求频率由调用方控制，不属于常驻开销。
