# 把 Qt 卡顿监控的自身开销压到 140ns：一个 ANR 看门狗的完整设计

## 一、问题：监控器不能成为新的卡顿源

给 Qt 桌面程序做卡顿排查，最讽刺的失败方式是：**为了抓卡顿而上身的监控，自己把程序拖卡了**。

先算一笔账。60 FPS 意味着每帧预算 16.6ms。一个常驻监控如果每个事件吃掉 10µs，在每秒 1 万次事件派发的界面（拖拽、鼠标移动、定时器风暴都会到这个量级）下，仅监控自身就吃掉 100ms/s ≈ 10% 的 CPU——这还没算它引发的缓存污染与唤醒开销。10µs 太贵了。我们的预算定得很苛刻：

- **全关常驻**：< 0.01% 帧预算（约 1.6µs 以内/事件）
- **开启监控**：依然亚微秒级
- **告警路径**：只有已经超阈值的事件付费——反正它已经卡了，多花几十微秒做"取证"不改变"已卡顿"的事实

最终实测：全关常驻 **~140ns/事件**（帧预算的 0.0008%），开启后 **610~952ns**，极端负载（每秒 10 万事件）CPU 占比估算 1.4%。这篇文章讲清楚这些数字是怎么来的、以及中间做对了什么、又有哪些取舍低于预期。

## 二、架构选型：为什么是 notify() 单点覆写

想拿到"每个事件耗时"，常见三条路：

| 方案 | 问题 |
|---|---|
| 给关键对象装事件过滤器 | 要逐个安装，覆盖不全；过滤器链本身有派发成本 |
| 在业务类里插桩 | 侵入业务代码，监控与被监控耦合，谈不上"组件" |
| **子类化 QApplication 覆写 notify()** | 全进程所有事件必经的单点，业务零侵入 |

第三条路的关键在于：`notify()` 是 Qt 事件系统的总闸——所有跨对象事件派发（含窗口系统事件、定时器、posted event）都从它走。子类化后业务侧只改一行（`QApplication` → `CusApplication`），监控链就完整装配了。

但"总闸"意味着**每一纳秒都要省**。覆写入口只做三件事：

1. `isEnabled()` 短路——全关时直接透传，这是 140ns 的主体路径；
2. `thread_local` 嵌套深度管理——防止事件处理器里再派发事件导致递归计时污染统计；
3. `EventGuard` RAII 计时——作用域结束自动结算，超阈值才走重路径（快照、格式化、落盘）。

热路径上没有任何堆分配、没有字符串格式化、没有锁竞争热点——这是 ①② 两条开销线保持在百纳秒量级的根本原因。

## 三、量化方法论：同进程对照法（全文最重要的部分）

性能数字最大的敌人不是优化，是**噪声**。跑分脚本 vs 生产代码路径、冷启动 vs 热身、机器负载波动——任何单一测量都可能撒谎。我们的 harness 用了三个手段：

**1. 同进程对照**。基线不是"另一个没装监控的程序"，而是同一进程里用限定名直调绕过覆写：

```cpp
// 基线：等价于未安装监控器的 Qt 原生分发
app.QCoreApplication::notify(receiver, &event);
// 被测：虚调用进入监控覆写
app.notify(receiver, &event);
```

两者之差即监控纯增量，机器噪声、事件本身成本在差值里全部抵消。

**2. 开销线分离**。不报一个笼统的"监控开销"，而是拆成四条独立的线：①覆写固定开销（全关常驻）、②正常路径（开启后低于阈值）、③告警路径（超阈值取证落盘）、④信号发射 spy 回调。每条线有独立触发条件与独立数字，优化时才知道动的是哪里。

**3. 多轮中位数 + 微样本不进门禁**。我们踩过一个典型的坑：告警路径的 benchmark 单次运行结果在 12~25µs 之间摆动（±40%）。原因不是代码变了，而是这条路径包含真实文件 IO，本身对调度噪声敏感。结论固化成两条纪律：**告警类场景至少 3 轮取中位**；**微样本场景不进 CI 漂移门禁**（漂移检测只看稳定的 ①②④ 线，±25% 容差）。

V5 终态四矩阵数据（Qt 5.15/6.5 × MSVC/MinGW，同进程对照增量）：

| 开销线 | 实测（ns/op） | 占 16.6ms 帧预算 |
|---|---:|---:|
| ① 覆写固定（全关常驻） | 160~182 | 0.001% |
| ② 正常路径（开启后） | 610~952 | 0.006% |
| ④ 信号 spy 回调 | +34~58 / emit | — |
| ③ 风暴抑制路径 | 15.6~18.6 µs | 仅超阈值事件付费 |
| ③ 完整告警路径 | 110~153 µs | 仅超阈值事件付费 |

## 四、三个诚实取舍

### 1. 风暴抑制：用 3.4× 换函数级归因

1ms 阈值下，风暴期每条慢事件都做"完整告警"（调用栈采集 + 格式化 + 4 sink 落盘）要 110~153µs。我们改成 1 秒抑制窗口：**首条必出完整告警，窗口内后续静默累计，窗口结束懒冲刷一条 `suppressed=N` 汇总**。风暴期单条成本降到 15.6~18.6µs——比 V2 全告警方案直接减半。代价是"窗口内第 2~N 条"没有独立栈：但风暴里它们大概率是同一问题，首条已带完整取证。

### 2. 栈采集三档：优化收益的归因经常和直觉相反

为风暴路径加档位（`StackCaptureMode`）：0=命中即采 / 1=仅窗口首条采 / 2=全免。mode=1 实测 16.8 → 10.7µs，**-36%**。拆解后发现一个反直觉事实：抑制路径的大头不是栈采集（仅 ~6µs），而是**告警日志格式化 + 结构化记录采集（~10µs）**——后者按"全量记录"语义必须保留。所以任何针对栈采集的进一步优化，天花板就是那 6µs。这个归因决定了后续投入方向。

### 3. 懒解析后移：-12% 低于预期，但架构收益是真的

V5 把字段解析从采集端整个搬到消费侧（环形缓冲只存原文，快照出口锁外 hydrate）。规划预估省 6~8µs，实测 **-12%（约 1.3µs）**——现代 allocator 下，解析的 ~20 次 substr 小分配远比估算便宜。诚实记录这个数字，但这步改造的真实收益在架构上：风暴期无消费则零解析、4096 条环形的内存占用下降、快照持锁时长缩短、解析逻辑单点化（上行聚合端直接复用同一个 hydrate 函数）。

**这三个案例共同的方法论：先量化归因，再动手优化；结果低于预期时如实落档**——错误的收益直觉比没有优化更危险，因为它会误导下一次投入。

## 五、可见性：ANR 看门狗与多进程聚合

抓单条慢事件只解决了一半问题；ANR（主线程长冻结）是另一类怪兽——事件循环本身停了，任何"事件回调里做检查"的方案都会一起停。

我们的看门狗走旁路：主线程心跳 QTimer + 常驻线程 100ms 轮询。冻结时事件循环卡死 → 心跳停跳 → 轮询线程发现超时，按 started / ongoing / recovered 三态告警，取证快照绑定心跳线程（否则 worker 线程的事件派发会污染冻结现场——这也是一个实测踩过的坑）。恢复判定 = 心跳重新前进，冻结时长 = 从最后心跳时刻起算。

多进程场景下，每个被监控进程经 Named Pipe 上行 NDJSON。这里的关键设计是**差量游标**：数据本体留在监控进程的环形缓冲里，客户端只持一个 seq 游标增量拉取式推送——上行通道断线、对端死掉，热路径增量都是 0；对端消费不及，语义是"环形覆盖 + skipped 计数"的背压丢弃，绝不阻塞监控线程。中心收集器（aggregator）按 pid 聚合，产出**零 JS 的自包含 HTML 报告**——医疗/工控等内网环境打不开 CDN，自包含是刚需。

## 六、数据出口与生态位

数据出口覆盖三个时间尺度：实时（外部进程 IPC 改阈值、tail 日志流）、事后（CSV / JSON / SQLite 全量回放 + 九段诊断报告 + 单进程/聚合 HTML）、归因（慢事件自动调用栈 ≤32 帧带模块归属）。

与现有工具的定位差异：QML Profiler / hotspot / VTune 是**开发期离线**工具，接入重、开销大，不适合常驻生产环境；QtEventWatcher 目标是**生产环境常驻**——140ns 的常驻成本让它可以随包发布，出问题现场就有全量数据，而不是"回开发机再复现一次"。
